## 2. Root Cause Analysis

| Symptom | Likely Cause | Supporting Evidence |
|---------|--------------|---------------------|
| **9 % error rate** | 1. **Server overload** – CPU/Memory saturated, causing timeouts or 5xx responses.<br>2. **Application bugs** – unhandled exceptions triggered by high traffic.<br>3. **Database contention** – slow queries causing timeouts. | 450 failed requests out of 5 000; error rate 9.2 % |

**Primary Root Cause:**  
The **combination of high packet loss and server overload** is the most likely driver. Packet loss forces retransmissions, inflating latency and causing timeouts. Simultaneously, the server is unable to process requests fast enough, leading to a high error rate.

## 4. Optimization Recommendations

### A. Immediate (0–24 h)

| Action | Rationale | Expected Outcome |
|--------|-----------|------------------|
| **Increase server capacity** (CPU/Memory) or **scale out** (add more instances). | Mitigates overload, reduces timeouts. | Lower error rate, reduced latency. |
| **Enable/Increase HTTP keep‑alive** and **connection pooling**. | Reduces TCP handshake overhead, especially for Postman. | Lower client‑side latency. |
| **Apply traffic shaping / QoS** on the edge router to prioritize API traffic. | Prevents packet loss due to congestion. | Packet loss drops below 1 %. |
| **Restart or hot‑swap problematic services** (e.g., database, cache). | Clears stuck connections or memory leaks. | Immediate performance lift. |
| **Check for network hardware faults** (NIC errors, link flaps). | Physical layer issues cause packet loss. | Packet loss resolved. |

### B. Short‑Term (1–7 days)

| Action | Rationale | Expected Outcome |
|--------|-----------|------------------|
| **Implement circuit breaker / bulkhead patterns** in the application. | Prevents cascading failures. | Error rate stabilizes. |
| **Add or tune caching** (e.g., Redis, CDN) for read‑heavy endpoints. | Offloads backend, reduces latency. | Lower P95 latency. |
| **Profile application code** (CPU, memory, GC). | Identify bottlenecks, long GC pauses. | Reduce tail latency. |
| **Upgrade TLS configuration** (use modern ciphers, enable session resumption). | Speeds up handshake, reduces latency. | Postman RT improves. |
| **Deploy a lightweight monitoring agent** (e.g., Prometheus node_exporter) to capture per‑second packet loss and latency. | Provides granular data for root‑cause analysis. | Better diagnostics. |

### C. Long‑Term (30 days+)

| Action | Rationale | Expected Outcome |
|--------|-----------|------------------|
| **Move to a managed load balancer** with health checks and auto‑scaling. | Offloads traffic distribution, improves resilience. | Sustained low error rate. |
| **Implement a CDN or edge caching** for static assets and API responses. | Reduces round‑trip time for clients worldwide. | Postman latency drops. |
| **Adopt a multi‑region deployment** with active‑active or active‑passive failover. | Reduces single‑point failure, improves latency for distant clients. | Global performance improves. |
| **Introduce a dedicated packet‑loss monitoring service** (e.g., NetFlow, sFlow). | Continuous visibility into network health. | Early detection of congestion. |
| **Conduct regular load testing** (e.g., k6, Gatling) to validate capacity. | Ensures that scaling decisions are data‑driven. | Confidence in SLA compliance. |

The monitoring snapshot shows a **service that is reachable but suffering from a high error rate (9 %) and significant packet loss (4.8 %)**. These two factors are the primary drivers of the degraded performance, especially the elevated client‑side latency observed in Postman.
